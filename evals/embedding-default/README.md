# embedding-default — choosing gbrain's default embedding model

_Follows `docs/eval/SEARCH_MODE_METHODOLOGY.md`: pre-registered expectations, paired bootstrap, Bonferroni correction, threats to validity named up front. Metrics resolve through `src/core/eval/metric-glossary.ts` so the terms match the rest of the repo._

## 1. The question, and why public benchmarks cannot answer it

gbrain needs a default embedding model. The decisive evidence does not exist publicly:

- **No public benchmark covers Hebrew at all.** Not MTEB, not MIRACL, not BEIR.
- **Only one covers Japanese**, behind a private split.

gbrain has confirmed users in both scripts: CJK entity extraction (#1637) and Hebrew slugs being stripped to data loss (#3417). Picking a default from an English leaderboard is picking blind for those users.

So this eval builds the missing measurement: **four language slices — English, Hebrew, Chinese, Japanese — over the same semantic topic set, on real text.**

## 2. What it measures, and what it does NOT

**Measures:** how well an embedding model alone ranks the right document for a query, per language, on a clustered in-domain corpus.

**Does NOT measure:**
- gbrain's end-to-end search quality. This is the **vector arm only** (see §5).
- Your brain's content or query distribution.
- Chunking, ingest, or extraction quality — every document is one chunk by construction.
- Cost or latency at production scale (embedding spend is a rounding error next to downstream model spend; see the cost anchors in `docs/eval/SEARCH_MODE_METHODOLOGY.md`).

## 3. Corpus — real text, honestly labelled

> **Documents are REAL.** Every document is a Wikipedia article plaintext extract (CC BY-SA 4.0), truncated to 2,000 characters, recorded with `pageid` + `revid` + `source_url` so the exact revision is re-fetchable. **No document in this corpus was generated by an LLM.**

| | value |
|---|---|
| Slices | `en`, `he`, `zh`, `ja` |
| Docs per slice | **80** — the *same 80 topics* in every language, resolved via the Wikipedia langlinks API |
| Doc source | Wikipedia article plaintext (`action=query&prop=extracts&explaintext`) |
| Doc length | median 2,000 chars in every slice (mean: en 2000, he 1919, zh 1864, ja 1885) |

Holding the topic set constant across languages is the point: **language and script are the only variables** between slices. A cross-slice difference is not a difference in topic difficulty.

The pool is deliberately **clustered** inside gbrain's own domain — AI labs, AI researchers, model architectures, retrieval/IR methods, datastores, venture funding (`topics.txt` documents each cluster). 80 unrelated topics would ceiling out at nDCG ≈ 1.0 for every model and measure nothing. Near-neighbour confusability is what makes the ranking task real: `postgresql`/`mysql`/`sqlite`, `chatgpt`/`claude`/`google-gemini`/`llama`, `k-nearest-neighbors`/`cluster-analysis`.

### Two query families, reported separately

| family | n (en/he/zh/ja) | origin | synthesis |
|---|---|---|---|
| `alias` | 209 / 94 / 159 / 116 | **Real** Wikipedia namespace-0 redirect titles on each language's own wiki | **none** |
| `nlq` | 24 / 24 / 24 / 24 | **Author-written** paraphrase questions | **queries only** (docs still real) |

**The `alias` family is synthesis-free.** A redirect on he.wikipedia is a surface form a Hebrew speaker actually typed and a Hebrew-speaking editor actually created. Nobody in this pipeline wrote it. It is the entity-lookup query shape that dominates gbrain traffic.

**The `nlq` family is author-written and labelled as such in every row (`"origin": "author-written"`).** 24 questions per language, each describing the target by *attribute* while deliberately avoiding the article's title wording, so the task is semantic retrieval rather than title matching. This family carries generator-phrasing bias — see §6.

**Ambiguous labels are dropped, not guessed at.** zh.wikipedia redirects "Claude 2" → the Anthropic article, but this corpus also contains a separate Claude (AI) document, so that query has two defensible gold answers while the qrel names one. `keepAlias()` drops any alias that also names a *different* corpus doc. A unit check pins this.

**Script verification.** Each query is tagged with its detected majority script. he.wikipedia redirects include Latin brand names ("NVidia"), which are not a test of Hebrew — so every headline claim is re-checked on an **`in_script` robustness group** that keeps only queries actually written in the slice's script (en 233, he 93, zh 138, ja 108). The conclusions get *stronger* there, not weaker.

### What the corpus does NOT contain

**No meeting-transcript / conversational documents, and no "what did X say about Y" queries.** Wikipedia has no multi-speaker transcript text in Hebrew, Chinese and Japanese over a shared topic set, and the alternative — LLM-generating transcripts *and* the queries against them — would put maximal generator bias on both sides of the measurement, producing a number too caveated to act on. This is a documented gap, not an oversight: gbrain's `meeting-ingestion` path is not covered by this eval. Filling it needs a real multilingual transcript source.

## 4. Candidates

| id | model | dims | note | status |
|---|---|---|---|---|
| `3-small@1280` | `openai:text-embedding-3-small` | 1280 | the incoming default | ran |
| `3-small@1536` | `openai:text-embedding-3-small` | 1536 | native width — is the 1280 truncation free? | ran |
| `3-large@1536` | `openai:text-embedding-3-large` | 1536 | Matryoshka-truncated from native 3072 | ran |
| `qwen3-0.6b@1024` | `ollama:qwen3-embedding:0.6b` | 1024 | open weights — cannot be sunset by a vendor | ran |
| `bge-m3@1024` | `ollama:bge-m3` | 1024 | second open-weight datapoint, multilingual-first training | ran |
| `gemini-embedding@1536` | `google:gemini-embedding-001` | 1536 | opportunistic — a `GEMINI_API_KEY` was present | ran |
| `voyage-3.5@1024` | `voyage:voyage-3.5` | 1024 | not keyed at receipt time | **skipped** |

**1280 dims is verified working** end to end on `text-embedding-3-small` — the gateway's Matryoshka `dimensions` passthrough and its dim self-check both accept it, and the returned vectors are 1280-wide.

Adding a candidate is a one-line edit to `CANDIDATES` in `harness-runner.ts`. Unkeyed providers declare `requires_env` and **skip with a message instead of failing the run**, so Voyage slots in with zero code change the moment a key exists. Google needed only an env alias (`GOOGLE_GENERATIVE_AI_API_KEY` ← `GEMINI_API_KEY`), declared as data on the candidate.

## 5. Method — vector-arm-only, deliberately

1. `configureGateway()` is called with an **explicit config object** per candidate. No gbrain config file is read; **`~/.gbrain` is never touched and no brain is opened.**
2. Documents and queries are embedded through gbrain's **real** `src/core/ai/gateway.ts` `embed()`, so provider options, Matryoshka `dimensions` passthrough, batching and the dim self-check are all the production code paths — not a re-implementation. Queries use `inputType: 'query'` so asymmetric providers get query-side encoding exactly as `embedQuery()` does.
3. Each query ranks **all 80 docs in its slice** by cosine similarity.
4. Scoring goes through the repo's own `recallAtK` / `mrr` / `ndcgAtK` from `src/core/search/eval.ts`.

**Why no hybrid search and no reranker.** gbrain's keyword arm, RRF fusion and cross-encoder reranker each partially *absorb* embedding-quality differences — a good reranker rescues a mediocre embedding's top-50. That is exactly why they are excluded: including them would measure the **system** and systematically **understate** the model delta. This run isolates the variable being chosen. The practical consequence is stated in §7: the end-to-end gbrain deltas will be **smaller** than these numbers.

A disposable PGLite brain would add nothing here — pgvector's cosine operator computes the same quantity as the harness's `cosine()`, over the same vectors, so it would produce the same ordering while adding ingest/chunking noise on top. The methodological cost of the shortcut is that gbrain's *own* SQL path is not exercised; that path is already covered by `test/e2e/engine-parity.test.ts`.

## 6. Pre-registered expectations

Fixed **before** the run, so the Bonferroni family is not chosen after seeing the data — which is the only thing that makes a multiple-comparison correction mean anything.

Pairs (`PAIRS` in `harness-runner.ts`), all four slices, three metrics → **Bonferroni factor 60**:

1. `3-small@1280` vs `3-small@1536` — is the 1280 truncation free?
2. `3-small@1280` vs `3-large@1536` — is the bigger OpenAI model worth it?
3. `qwen3-0.6b@1024` vs `3-small@1280` — does open-weight beat the default?
4. `bge-m3@1024` vs `3-small@1280` — second open-weight vs the default
5. `qwen3-0.6b@1024` vs `bge-m3@1024` — which open-weight model?

**Expected:**

1. **1280 vs 1536 lands within noise.** Matryoshka truncation at 83% of native width should cost little. → **CONFIRMED**
2. **`3-large` beats `3-small` by 2-5pp nDCG@10, uniformly across slices.** → **PARTLY WRONG.** It wins everywhere, but the margin is wildly non-uniform: +3pp on English, **+17pp on Hebrew**.
3. **Open-weight models lose to OpenAI on English, and roughly tie on CJK.** → **WRONG in the direction that matters.** They lose slightly on English and win decisively on Hebrew (+21 to +28pp).
4. **No slice falls below the nDCG@10 ≥ 0.65 "ship it" threshold.** → **WRONG.** `3-small` on Hebrew scores 0.625 (0.596 in-script), *below* the threshold.

Three of four pre-registered expectations were wrong. That is recorded here rather than buried, per the methodology doc.

## 7. Results

Full tables, per-query rows and every bootstrap CI: `baseline-runs/2026-07-28-report.md`, `-report.json`, `-run.jsonl`.

**nDCG@10, all query families** (n = 233 / 118 / 183 / 140):

| model | en | he | zh | ja |
|---|---|---|---|---|
| `3-small@1280` (incoming default) | 0.9290 | **0.6253** | 0.9024 | 0.8328 |
| `3-small@1536` | 0.9324 | **0.6229** | 0.9031 | 0.8320 |
| `3-large@1536` | 0.9626 | 0.7930 | 0.9510 | 0.9307 |
| `qwen3-0.6b@1024` | 0.8978 | 0.8389 | 0.9364 | 0.8676 |
| `bge-m3@1024` | 0.9146 | 0.9083 | 0.9502 | 0.8879 |
| `gemini-embedding@1536` | **0.9678** | **0.9556** | **0.9796** | **0.9691** |

**Same table, `in_script` robustness group** (wrong-script queries dropped; n = 233 / 93 / 138 / 108):

| model | en | he | zh | ja |
|---|---|---|---|---|
| `3-small@1280` | 0.9290 | **0.5961** | 0.8852 | 0.8040 |
| `3-small@1536` | 0.9324 | **0.5956** | 0.8882 | 0.7984 |
| `3-large@1536` | 0.9626 | 0.7475 | 0.9450 | 0.9148 |
| `qwen3-0.6b@1024` | 0.8978 | 0.8017 | 0.9261 | 0.8614 |
| `bge-m3@1024` | 0.9146 | 0.8876 | 0.9466 | 0.8673 |
| `gemini-embedding@1536` | **0.9678** | **0.9437** | **0.9783** | **0.9652** |

### The three findings

**(1) The 1280 truncation is free.** Every one of the 12 `3-small@1280` vs `@1536` comparisons is **not significant**, with tight CIs straddling 0. Largest nDCG@10 effect: −0.0033 on English, CI [−0.0077, 0.0000], adjusted p = 1.0. Largest effect on any metric: −0.0085 Recall@10 on Hebrew, adjusted p = 1.0. Keep 1280 and save 17% of vector storage.

**(2) `text-embedding-3-small` fails Hebrew.** 0.625 nDCG@10 (0.596 in-script) against 0.929 on English — a **30-point collapse**, below the repo's own 0.65 ship-it threshold. On author-written Hebrew questions specifically it scores **0.349**. Both open-weight models beat it by a margin that survives Bonferroni-60 on the in-script group:

| comparison (he, in_script) | Δ nDCG@10 | 95% CI | adj. p | verdict |
|---|---|---|---|---|
| `bge-m3@1024` − `3-small@1280` | **+0.2915** | [0.2209, 0.3656] | 0.0000 | **significant** |
| `qwen3-0.6b@1024` − `3-small@1280` | **+0.2057** | [0.1304, 0.2852] | 0.0000 | **significant** |
| `3-large@1536` − `3-small@1280` | +0.1514 | [0.0955, 0.2105] | 0.0000 | **significant** |
| `bge-m3@1024` − `qwen3-0.6b@1024` | +0.0859 | [0.0419, 0.1334] | 0.0000 | **significant** |

**A 0.6B open-weight model that runs on a laptop beats the incoming hosted default by 21-29 points on Hebrew.** That is the result no public benchmark could have told the maintainer.

**(3) On English, everything is within noise; the ranking only separates off-English.** `qwen3` and `bge-m3` vs `3-small@1280` on English: no significant difference on any metric (adjusted p 0.48-1.0). The models are interchangeable on English and very much not interchangeable on Hebrew. **An English-only eval would have concluded "any of these is fine."**

Secondary: `gemini-embedding-001` wins every slice and is the only candidate above 0.94 everywhere. `bge-m3` beats `qwen3-0.6b` on Hebrew (significant) and ties elsewhere, so it is the better open-weight pick.

## 8. Threats to validity

Named so a critic does not have to find them.

- **The `nlq` family's queries are LLM-authored.** Documents are real, queries are not. A model whose training distribution is closer to the query author's phrasing is flattered. Mitigation: the `alias` family is fully synthesis-free and shows the **same ordering**, so the headline conclusion does not rest on the authored queries. But the *absolute* `nlq` numbers are indicative only.
- **Author-written non-English queries may read non-natively.** The Hebrew/Chinese/Japanese `nlq` phrasings were written by an LLM, not by native speakers. A native-speaker review could shift the `nlq` numbers. The `alias` family — real editor-written surface forms — is the defence, and it agrees.
- **Small n, one run, one seed.** 93-233 queries per slice; 24 per slice in the `nlq` family, which is at the low end of the requested 20-40 floor. Single run with `seed 42`; no across-run variance estimate. Embedding APIs are near-deterministic, so re-run variance should be small, but it is unmeasured.
- **Wikipedia is not a brain.** Encyclopedic prose is cleaner and better-structured than real notes, meeting transcripts, or half-finished pages. It also very likely appears in every candidate's pretraining data, which may compress differences between models. Absolute scores are optimistic; the cross-language *deltas* are the transferable result.
- **Doc length is a partial confound.** Hebrew and CJK articles are shorter than English ones on the same topic (mean 1919/1864/1885 vs 2000 chars). Character counts are also not comparable across scripts — a Han character carries more information than a Latin one. So "Hebrew is harder" is partly "Hebrew documents are shorter here." The effect is small relative to a 30-point gap, but it is real.
- **Vector-arm-only overstates the end-to-end impact.** gbrain's keyword arm, RRF and reranker will recover some of the gap. The deltas here are an **upper bound** on what changing the default buys in production. That is the deliberate trade for isolating the variable (§5).
- **Single-gold qrels make the three metrics near-redundant.** With one relevant doc per query, Recall@10 is a hit-rate and nDCG@10 is a monotone function of the gold rank, so nDCG@10 and MRR correlate strongly. They are not three independent pieces of evidence. Recall@10 also **saturates** — `gemini` hits 1.0000 on three slices — so it discriminates poorly at the top; read nDCG@10 and MRR instead.
- **80-doc pools are small.** A production brain has 10K-100K pages, where near-neighbour confusion is far worse. Absolute scores would drop for everyone.
- **Bonferroni-60 is conservative** and will call real-but-modest effects "not significant" (e.g. `bge-m3` > `3-small` on Japanese nDCG@10: raw p = 0.0012, adjusted 0.072). Raw p-values are reported alongside so readers can judge.
- **`gemini-embedding` was opportunistic, not planned.** It is not in the pre-registered pair list, so its comparisons carry no multiple-comparison budget. Treat it as a strong signal that deserves its own pre-registered run, not as a tested conclusion.

## 9. Recommendation, with its uncertainty

**On the primary question — 1280 vs 1536 for `text-embedding-3-small` — ship 1280. That result is solid.** 12/12 comparisons not significant, tight CIs around 0, and it saves 17% of vector storage. Low uncertainty; this is a real "within noise" finding, and within-noise is the useful answer.

**On the default model, the honest answer is: `text-embedding-3-small` is the wrong default if gbrain intends to serve Hebrew users.** It falls below the repo's own 0.65 nDCG@10 ship-it threshold on Hebrew while a laptop-sized open-weight model clears 0.88. This is not a within-noise result — it survives a factor-60 Bonferroni correction on the robustness group with CIs nowhere near 0.

Ranked, with confidence:

1. **`gemini-embedding-001` @1536 — best measured, lowest confidence.** Wins all four slices, only candidate above 0.94 everywhere. But it was opportunistic and outside the pre-registered family. **Needs its own pre-registered run before it becomes the default.**
2. **`bge-m3` @1024 — best open-weight, good confidence.** Statistically indistinguishable from `3-small` on English, decisively better on Hebrew (+0.29, adj. p < 0.0001), better on Chinese, and it beats `qwen3-0.6b` on Hebrew. Open weights cannot be sunset by a vendor, and it runs locally at zero marginal cost. **The strongest recommendation this corpus supports.**
3. **`text-embedding-3-large` @1536 — the low-risk hosted upgrade.** Beats `3-small` on every slice, same provider, same API, one config key. Still only 0.75 in-script on Hebrew — better, not fixed.
4. **`text-embedding-3-small` @1280 — fine for an English-only brain, and only that.**

**What would change this verdict:** a native-speaker pass over the Hebrew and Japanese `nlq` queries; a second seed and a real corpus of non-encyclopedic notes; a hybrid+reranker run to size how much of the gap gbrain's own pipeline already absorbs; and Voyage keyed in.

## 10. Reproduce

```bash
# Corpus (already committed; only needed to rebuild from Wikipedia).
node evals/embedding-default/build-corpus.mjs --refetch

# Full sweep. Skips any candidate whose key is absent.
export OPENAI_API_KEY=...            # 3-small, 3-large
ollama serve && ollama pull qwen3-embedding:0.6b && ollama pull bge-m3
node evals/embedding-default/harness.mjs

# One candidate, or a custom output dir.
node evals/embedding-default/harness.mjs --candidates=bge-m3@1024 --out=/tmp/x

# Re-derive the report from a committed run, zero API cost.
node evals/embedding-default/harness.mjs \
  --rescore=evals/embedding-default/baseline-runs/2026-07-28-run.jsonl

# Checks (no key, no network).
bun test evals/embedding-default/harness-runner.test.ts
```

**Cost:** ~$0.05 total for the three OpenAI candidates plus Gemini (4 slices × 80 docs × ~500 tokens + ~700 queries each). Ollama candidates are free and finish in ~80s each on an M-series laptop.

## 11. Receipt

`baseline-runs/2026-07-28-run.jsonl` opens with a receipt row binding `run_id`, `ran_at`, `harness_sha`, `corpus_sha256`, `topics_sha256`, `seed`, `k`, `bootstrap_resamples`, `retrieval_arm`, the candidate list, the skipped list, the pre-registered pairs and the Bonferroni factor — then one row per (candidate × slice × query) carrying the gold rank and all three metrics. Anyone can re-score it with their own metric implementation.

Per-run records also append to `<repo>/.gbrain-evals/eval-results.jsonl` per `docs/eval/SEARCH_MODE_METHODOLOGY.md` §4. **The user's personal `~/.gbrain` brain is never read or written.**

## 12. Why this lives in `evals/`, not `skills/`

The skillpack bundler walks `skills/<skill>/` recursively, so eval infrastructure placed there would ship to every downstream install. Same precedent and same reason as `evals/functional-area-resolver/`. Importing `src/core/ai/gateway.ts` is legitimate from here because this is a gbrain-repo-only maintainer tool.
